# Read-only audit: paired child relation inheritance

Status: open dependency analysis, not a theorem or checked counterexample.

The SAME ObservedPut relation uses StructuralClassKey.key of its prepared preminimum package, root raw-variable-rank equality, original candidate domain, and all-position paired key/rank tests. This is not the hereditary evaluator relation.

## Application

OriginalStructuralClassKeyDefinitions.core is the prior structural traversal. It opens applications and rebuilds the original constructor from the two child core outputs. A prospective inverse theorem could recover corresponding child core outputs from equality of parent outputs, after proving the actual source/constructor interfaces and constructor injectivity. Existing ApplicationCongruenceLaw and OriginalPositionStructuralKeyApplicationTargets.ActualApplication run in the opposite direction: they consume child observations and produce parent observation equality.

Even if inverse key equality is paid, root rank and deletion-position rank equalities at an application are additive parent observations. Equality of the two sums alone does not establish equality of either corresponding child rank. Accepted at each child needs those individual rank tests. No applicable exact rank-determinacy-from-structural-key theorem was found in this audit. The prior key is not definitionally the newly rank-guarded final tuple, and replacing it by the hereditary evaluator would be an unauthorized mathematical substitution.

## Lambda

The actual child parameter prepends the domain type to Gamma. Parent cutoff j is transported to child cutoff suc j in the accepted forward lambda observation theorem. Thus parent all-position tests cover shifted old-context positions, but the child's own all-position relation additionally tests cutoff zero, deletion of the newly bound variable. Neither parent root structural-key equality nor the existing forward congruence contract supplies that missing child deletion observation by itself. An internal erasure congruence theorem for the SAME structural key, or another genuine bound-zero argument, would be needed.

## What is and is not established

The current normalization result proves parent final input/output relation acceptance and equality of their actual once-minimum outputs. It does not prove that every pair accepted by that relation has accepted corresponding children, or that complete final folds factor through that minimum.

These are unpaid logical components in a proposed proof route, not demonstrated counterexamples. No new target should silently assume child ranks, child allTests, bound-zero erasure agreement, or child Accepted while claiming unconditional parent-to-child inheritance. Further source analysis or a genuine same-tuple counterexample is required before choosing the next exact endpoint.

## Follow-up: can the prior core itself determine rank?

The actual pre-key core opens application and lambda only. OTHER roots, including ordinary and numbered constructors whose payloads can contain variables, use the selected prior leaf. OriginalConstructorShape.mark observes only root tag and application domain; OriginalVariableRepresentative.variableMark distinguishes whole variables from nonvariables; OriginalFunctionNeutrality.mark observes neutral applications; BottomSpineMeasure observes the function-spine flag/depth. These do not individually observe variable occurrence counts nested beneath ordinary/numbered roots.

The current prepared PUT/mixed path refinements modify oldStep; they do not install the later OriginalRankGuardedRepresentative into this prior key. Therefore a structural-core rank decoder would first need a genuine OTHER-leaf rank-determinacy theorem. A constructor weighted-sum proof alone cannot discharge that leaf obligation.

A concrete candidate counterexample route is an arbitrary oldRepresentative mapping a same-type ordinary(var0) to ordinary(bottom), while keeping ordinary(bottom) fixed. Root-only guards would not distinguish their inner occurrence counts. This is NOT a verified witness: actual source guards, bounded-descent selection, relative codes, and all relevant graph computations still need checking. It must not be cited as a counterexample until those steps are established.
